In-Context Prompting取代Agent编排研究

共识是可少写编排，但上下文治理会成为新瓶颈。

查看原始测评

观察：Neo4j 的第三方分析直接点出现实中的 agent 常见失效：会丢失自己的计划、反复调用错误工具，问题根源往往不是单条 prompt 不好，而是动态任务状态与上下文管理失控。

改变：这意味着团队若改用更强的 in-context/context engineering，把状态、工具结果和用户目标直接作为上下文组织清楚，可能减少专门写程序编排来纠正 agent 走偏的需求。

边界：它同时强调静态 prompt 处理不了持续演化的任务状态，所以这并不适合长链路、高状态依赖但又缺少上下文治理能力的场景。

— Neo4j

观察：Sean Falconer 在第三方实务指南里把 prompt、workflow、agent 明确分层：prompt 更适合单次、孤立、上下文固定的任务，而 workflow 是把这类能力扩展成由代码预定义步骤的序列。

改变：对用户和团队的真实改变是，若论文所说的 in-context prompting 成立，它更像是在把一部分原本要写成 workflow 的步骤重新吸收到上下文里，从而减少显式编排代码。

边界：但该文也给出清晰边界：一旦任务不是固定上下文、而是多步且需稳定执行预定义流程，单靠 prompt 仍未必比代码 workflow 更稳。

— Sean Falconer / Medium
OpenClaw外部测评/真实影响 CrowdStrike / NSFOCUS / ltesting.net

OpenClaw案例下自主Agent框架攻防综述

共识是OpenClaw风险主要来自高权限自治，价值取决于限权与隔离是否先到位。

查看原始测评

观察：CrowdStrike观察到，OpenClaw一旦被赋予API、数据库和业务系统的合法访问权，提示注入就不再只是改写回复，而会被代理以机器速度自动放大成跨系统执行的真实入侵。

改变：这会直接改变团队的部署方式：不能再把Agent当聊天机器人接入生产，而要把它视为高权限自动化账户来做最小权限、工具白名单和数据入口隔离。

边界：如果场景本身依赖高自治和多系统联动，安全控制会显著压缩可用能力；尤其不适合把未过滤的外部内容直接喂给能执行敏感操作的Agent。

— CrowdStrike

观察：NSFOCUS在攻击面分析中指出，OpenClaw连接的外部信息源和工具越多，恶意指令越容易失控，攻击入口不只来自提示词，还可能来自邮件、网页和聊天上传文件等间接输入。

改变：这意味着用户工作流要从“给Agent更多连接器提升效率”转向“先做输入分级和执行链隔离”，否则日常邮件、网页抓取、文件处理都会变成潜在攻击面。

边界：高度自治的OpenClaw不适合直接承担高风险操作，特别是那些本应由多重验证和凭证隔离保护的敏感任务。

— NSFOCUS
