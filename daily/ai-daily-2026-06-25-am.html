OpenHarness风格Agent Runtime设计教程

共识是它更偏开发者底座，核心价值在执行、记忆与协作控制。

查看原始测评

观察：第三方作者把 OpenHarness 运行时拆成一条决策链：模型负责决定，harness 负责执行，安全、记忆和多 Agent 协调夹在中间。

改变：这会把开发重心从“调一个更聪明的模型”转到“设计执行边界、记忆流转和协作流程”。

边界：更适合做代理基础设施，不是直接面向最终用户的聊天界面。

— OpenHarness Study

观察：另一篇深度解读明确指出，OpenHarness 把权限、工具、memory 和续跑逻辑当作产品边界，而不是把模型本身当边界。

改变：团队在接入 LLM 时能更系统地控制工具调用、权限和会话延续，减少把这些能力散落在业务代码里的问题。

边界：这类设计会增加运行时编排复杂度，没必要给只做单轮问答的场景上这一层。

— repo-explainer.com
Claude Opus/Sonnet高考志愿Agent工作流实测 翔宇工作流 / CSDN博客 / 七牛云行业应用（博客园）

Claude Opus/Sonnet高考志愿Agent工作流实测

共识是 Sonnet 适合分工执行，Opus 更适合长链路总控。

查看原始测评

观察：翔宇工作流的 Claude Code 实操指南提到，日常任务约 80% 用 Sonnet 即可，只有需要更深推理时才切到 Opus。

改变：这意味着做高考志愿 Agent 这类多步骤流程时，可以把资料整理、信息检索、表格生成等常规环节交给 Sonnet，把院校策略判断或复杂冲突决策留给 Opus，从而明显压低整体调用成本。

边界：边界是 Sonnet 更偏性价比路线，遇到高复杂度推理仍需要手动切到 Opus，否则结果深度可能不够。

— 翔宇工作流

观察：CSDN 的对比解读指出，Sonnet 4 在多 Agent 系统里很适合作为子 Agent，尤其擅长搜索、检索、定向审查这类专项任务，但长时间保持逻辑连贯和上下文一致仍有挑战。

改变：对志愿填报工作流来说，更合理的做法是把 Sonnet 放在信息收集、规则核对、分任务执行层，而不是让它单独承担全链路决策，这能提升流程稳定性。

边界：边界是如果工作流链路很长、上下文很多，Sonnet 可能出现一致性下降，需要靠 token 上限、任务拆分或更强主模型兜底。

— CSDN博客

GLM 5.2本地模型接入Cursor与Codex

共识是能顺利接入现有 IDE 工作流，但能力上更像可用备选，尚非顶配替代品。

查看原始测评

观察：第三方接入教程实测把 GLM-5.2 作为 OpenAI 兼容后端接入 Cursor/Claude Code/Cline 时，真正决定能否跑通的是 base URL、model id、上下文窗口和超时参数这些细节配置。

改变：对已经在用 Cursor 一类 IDE Agent 的个人和团队来说，这意味着不用重建工作流，只改接口参数就能把 GLM-5.2 接进现有编码助手链路里试跑。

边界：代价是配置容错很低，model id、超时或上下文参数写错就可能直接不可用，接入门槛主要不在功能而在细节对齐。

— Apidog 博客

观察：开发者评测认为 GLM-5.2 是其用过最强的国产模型之一，和 GPT、Claude 顶级模型的差距已经缩小，但还没到可以直接替代的程度。

改变：这对想把 GLM-5.2 接入 Cursor 或 Codex 类工具的用户意味着，它更适合作为日常编码与问答的国产备选后端，而不是无脑替换原有最强模型。

边界：在需要顶级稳定性、复杂推理或高难代码任务时，作者明确认为它仍不适合完全替代 GPT/Claude。

— 掘金作者评测
