DSPy优化Datasette Agent SQL提示词评测 Haystack / Prem / ADaSci

DSPy优化Datasette Agent SQL提示词评测

外部经验的共识是：DSPy能系统化优化SQL提示词，但前提是有可验证的数据与评测集。

查看原始测评

观察：Haystack 的上手指南明确把 DSPy 提示词优化写成一个“训练集优化、开发集评估”的流程，说明这类 SQL Prompt 改进不是拍脑袋改文案，而是依赖样本集反复验证效果。

改变：这对 Datasette Agent 这类 Text-to-SQL 工作流的真实意义是，团队可以把 system prompt 调整变成可复现的评测流程，减少只靠人工试几句的主观调参。

边界：代价是必须先准备有代表性的查询样本并做数据划分；如果没有足够贴近真实问题的 SQL 例子，优化结果很容易失真。

来源：Haystack

观察：Prem 的 Text-to-SQL 教程直接演示了用 `dspy.Signature`、`dspy.Module` 和 `dspy.teleprompt` 搭建并自动优化 SQL 生成链路，外部作者实际观察到 DSPy 可以用于提升 Text-to-SQL Prompt 的实际产出。

改变：对用户而言，这说明像 Datasette Agent 这样的 SQL 代理不必完全依赖手写 prompt，可以把 SQL 生成能力纳入可迭代优化的流水线，从而更快比较不同提示词方案。

边界：这套方法更适合输入输出边界清晰的 Text-to-SQL 任务；如果代理任务混入大量开放式推理或工具编排，单靠 prompt 优化未必就能稳定提升。

来源：Prem

Orca多智能体并行开发与Git工作树合入演示

外部共识是：Orca真正改变的是多Agent并行比稿与合并流程。

查看原始测评

观察：第三方拆解认为，Orca把每个 feature 放进独立的 git worktree，让 Codex、Claude Code、OpenCode 等 CLI Agent 能在同一窗口并行运行，而不是共用一个代码目录互相覆盖。

改变：这会把“多模型轮流试错”改成“多模型同时产出候选实现”，团队可以直接并排看结果，减少上下文切换和分支冲突。

来源：txtmix / StablyAI Orca 深度拆解

观察：上手文章指出，Orca把 git worktree 提升为 IDE 的核心对象：每个任务都是独立磁盘目录，并且各自带自己的 Agent、终端、浏览器，最后可在 IDE 内直接对比多个 worktree 的 diff 再挑一个合并。

改变：这对真实工作流的改变是，评审重点从“先选哪个 Agent”变成“先让多个 Agent 各跑一版，再基于 diff 选最优实现”，更适合需要快速比较方案的开发场景。

来源：知乎专栏 / Orca：把 5 个 AI 编码 Agent 塞进同一个 IDE 并行开干的开源工作台

外部测评 / 上手体验 知乎专栏《RAG-Anything：解锁多模态文档解析的下一代RAG引擎》 / 知乎专栏《RAG-Anything：构建一体化检索增强生成多模态AI系统的完整指南》

RAG-Anything多模态检索Colab教程实战

共识是它能做跨模态问答，但真正可用性取决于预处理和分块调优。

查看原始测评

观察：知乎作者在示例中先完整解析论文PDF，再用`query_with_multimodal(..., mode="hybrid")`追问“图2”和“表3”是否矛盾，强调RAG-Anything能把图表与正文关联后做跨模态检索问答。

改变：这意味着做Colab实战时，用户不只是检索段落文本，而是能直接围绕论文里的图、表、正文做联合追问，减少人工翻图表和交叉比对的步骤。

边界：这类能力依赖前置的完整文档解析与混合检索流程，文档预处理更重，轻量级纯文本问答场景未必划算。

来源：知乎专栏《RAG-Anything：解锁多模态文档解析的下一代RAG引擎》

观察：另一篇知乎实战总结把“保留多模态上下文的智能分块”列为生产级优化重点，说明作者在规模化使用中观察到，若分块只按长度切分，会破坏图文表之间的上下文关系，因此需要额外设计`max_chunk_size`和`overlap`策略。

改变：对真正要把教程跑成可用工作流的团队来说，重点不只是把Demo跑通，而是要把分块策略调到既保留跨模态关系又控制上下文长度，否则检索质量会明显波动。

边界：代价是需要额外调参与工程实现，文档结构越复杂，分块策略越难一次设对，不适合只想零配置快速上线的场景。

来源：知乎专栏《RAG-Anything：构建一体化检索增强生成多模态AI系统的完整指南》
