Claude Opus/Sonnet志愿Agent工作流实测

共识是Sonnet适合铺量，Opus适合复杂决策与长链路。

查看原始测评

观察：知乎作者引用 OSWorld 真实计算机任务基准称，Claude Sonnet 4.5 在“计算机使用”能力上拿到 61.4% 并居首，说明它在多步骤界面操作和工具调用场景里较前代有明显跃升。

改变：这意味着用 Sonnet 搭建志愿填报这类 Agent 工作流时，更有机会把网页检索、表单操作、信息整理等串行步骤交给模型自动完成，而不只是停留在问答层。

边界：这条结论主要来自基准成绩，能说明通用代理执行力提升，但不能直接等同于志愿填报场景里的稳定准确率或低幻觉。

来源：知乎博主《最强编程和agent模型Claude Sonnet 4.5来了！》

观察：YingTu 的对比文章认为，Claude Sonnet 4.6 应作为多数任务的默认模型，而 Opus 4.7 更适合高风险推理、模糊架构设计、长时运行 Agent、重文档综合和反复验收失败的任务。

改变：对团队搭建志愿填报 Agent 的直接意义是：可以先用 Sonnet 跑大部分高频、成本敏感流程，把复杂政策理解、疑难案例复核、长链路失败重试再升级给 Opus，形成分层调度。

边界：边界是 Opus 的高成本只有在任务确实复杂、失败代价高时才值得，否则默认上 Opus 会拉高运行成本并降低规模化效率。

来源：YingTu

GLM 5.2本地模型接入Cursor/Codex教程

共识是它已能进入真实编码代理工作流，但成本、部署和场景适配仍决定是否值得接入。

查看原始测评

观察：第三方分析文章把GLM-5.2放到Terminal-Bench、部署方案和API定价里一起看，给出的核心判断是它的编程能力已可对标Claude Opus 4.8这一档开源外替代方案。

改变：这对想把GLM 5.2接入Cursor、Codex或经OpenRouter调用的开发者来说，意义是可以把它当成一条更偏“能用且可算成本”的编码工作流选项，而不只是跟风尝鲜。

边界：文章同时强调部署方案和API定价，说明它的价值成立前提仍取决于你的部署能力与成本预算，并不等于所有团队都能零门槛替换闭源模型。

来源：自游人（GLM-5.2 开源全解析：评测数据、部署成本、竞争格局）

观察：实测文章把GLM-5.2放进代码执行和Agent任务中测试，并明确拿它与Claude Fable 5、Opus 4.8做性能差异对比，结论是其Coding与代理式任务能力都很强。

改变：这意味着用户在Codex这类代理式开发环境里接入GLM 5.2时，预期不应只停留在补全代码，而可以把它用于执行、拆解和推进多步开发任务。

边界：但该结论来自特定实测任务与竞品对比，能说明它适合Agent工作流，不等于在所有编程场景里都稳定优于Claude系模型。

来源：ProgramNotes（实测GLM-5.2，国产Coding模型的又一座新高峰）

DeepSeek V4 外部测评 HolySheep AI / 腾讯云开发者

DeepSeek V4百万token降本80%实测解析

外部实测共识是：V4在RAG里更吃工程链路优化，而非只看模型参数。

查看原始测评

观察：HolySheep AI 的实战文章称，在把 DeepSeek V4 的整套 RAG 链路切到国内中转通道后，单条请求平均延迟从 1.8 秒降到 47 毫秒，整条 RAG pipeline 跑完只用了 1 小时 22 分钟。

改变：这说明对做知识库问答的团队来说，真正影响体验的不只是模型本身，接入链路和调用路径优化后，RAG 可从“能用”变成更接近实时交互。

边界：这类提速建立在特定中转通道和整套链路重构之上，不等于直接调用官方 API 就能得到同样时延表现。

来源：HolySheep AI

观察：腾讯云开发者文章给出的企业级 RAG 实测结果是，在 10 万+ 文档场景下，基于 DeepSeek V4、LangChain 和 ChromaDB 的系统检索准确率达到 89%，响应时间控制在 2 秒以内。

改变：这对企业用户的真实意义是，DeepSeek V4 在私有知识库问答里已能支撑较大文档规模，团队可以把它用于内部技术文档检索，而不只是做演示级 Demo。

边界：这组结果依赖文档切片、向量嵌入和 ChromaDB 检索链路配合，表现反映的是完整 RAG 工程效果，不等同于模型裸能力，也未说明对弱结构化资料或更高并发场景是否同样成立。

来源：腾讯云开发者

AI小说提示词工作流教程下篇

第三方观察普遍认为，价值在于把小说写作拆成可复用流程，而非一次性生成。

查看原始测评

观察：什么值得买的上手文提到，蛙蛙写作这类“AI写网文”工作流允许用户自己搭表单、设计提示词、调试单个AI工具，再把多个工具编排成一个可重复调用的工具组。

改变：这意味着创作者不必每次从零重写提示词，而是能把拆书、设定、生成、润色等步骤固化成流程，降低新手上手门槛并提升批量写作效率。

边界：代价是前期需要自己理解并配置提示词与工具链，适合愿意折腾流程的人，不适合只想即开即写的用户。

来源：什么值得买

观察：GitHub上的第三方调研认为，蛙蛙写作更像“网文创作生产线+AI工具箱+工作流广场”，其交互核心不是单次生成，而是把大纲、角色、章节续写、润色、扩写、灵感和工作流能力嵌进同一个编辑过程。

改变：对用户和小团队来说，真正的改变是长篇小说创作从“单轮问答”转向“持续编辑+分环节调用工具”，更适合管理长文本的一致性与多步骤协作。

边界：这种设计更偏长篇网文生产流程，对只需要短内容、一次性文案或极简聊天式创作的人来说可能显得重。

来源：GitHub 调研文档《蛙蛙写作与星月写作AI工具工作流调研》
